# 产品、渠道与终端组合问题模拟数据

运行 `node data/generate_data.js` 可用固定随机种子重新生成 `low_user.json`、`high_user.json`、`all_user.json` 和 `业务订购.csv`。运行 `node data/check_data.js` 校验字段关联、样本分布和挖掘阈值。用户、服务人员与渠道代码均为虚构标识；四个数据文件保留原示例的字段格式。每名用户有一条触点记录和一条可通过 `phone` 关联的订购记录。

## 五个分析分组

每个 `action + main_object_l1 + main_object_l2` 分组有 80 名用户，其中低分 16 名、高分 64 名。设计中 `min_support = 0.15`、`lift_threshold = 1.5`，不设置最低支持人数。支持度和 Lift 均以**对应分析分组内**的用户为分母。

| 分组 | 目标项 | 运营商可处理的问题 | 低分 / 高分命中 | 低分支持度 | 低分对高分 Lift | 低分对全量 Lift |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| `咨询投诉 + 套餐业务 + 办理与权益使用` | 畅享视频套餐 + 省营业厅小程序（C101）+ 苹果 | iPhone 领取视频权益时页面空白、跳转失败或提示不支持；可核查权益跳转与补发流程 | 5 / 5 | 0.3125 | 4.00 | 2.50 |
| `咨询投诉 + 套餐资费 + 优惠与计费` | 悦享音乐套餐 + 线下营业厅（C202） | 柜台承诺首月免月费，账单却照常计费；可核查门店宣传、活动资格录入及费用处理 | 6 / 11 | 0.3750 | 2.18 | 1.76 |
| `咨询投诉 + 套餐业务 + 生效时点与流量使用` | 安心流量包 + 省营业厅小程序（C101） | 办理页提示立即生效，订单实际显示次日生效；可核查页面说明、受理流程及期间流量费用 | 6 / 11 | 0.3750 | 2.18 | 1.76 |
| `投诉质疑 + 套餐业务 + 通话分钟数变化` | 青禾通讯加盟店（C303） | 柜台办理套餐后可用通话分钟数减少，办理时未明确告知；可核查新旧语音权益和门店办理说明 | 8 / 18 | 0.5000 | 1.78 | 1.54 |
| `投诉质疑 + 业务订购 + 业务短信与订购确认` | 锦城路服务厅（C404） | 办理套餐后收到未主动订购的其他业务开通短信；可核查短信触发、受理流水及费用状态 | 8 / 18 | 0.5000 | 1.78 | 1.54 |

第一类问题按“产品 + 渠道 + 终端厂商”发现。两类产品渠道问题按“产品 + 渠道”发现，各有 6 名低分用户在 VOC 中描述同一种业务现象。对应产品渠道下，苹果、华为、小米终端各有 **2 名**低分用户，所以任何一个厂商细分组合的低分支持度都是 `2 / 16 = 0.125`，未达到 0.15。型号细分的支持度也不足。若把 4G/5G 当作终端项继续挖掘，4G 细分组合虽达到支持度，但低分对高分 Lift 约为 **1.45**、低分对全量 Lift 约为 **1.33**；5G 细分组合支持度不足。两类产品渠道问题都不会通过三维组合的完整筛选条件。

最后两个问题按**渠道单维**发现。每个目标渠道下的 8 名低分用户分散在四种产品和四个终端厂商中，每个产品、厂商各有 2 人，单一细分的低分支持度 `2 / 16 = 0.125`。如果继续按 4G/5G 细分，4G 细分虽达到支持度，但低分对高分 Lift 约为 **1.33**、低分对全量 Lift 约为 **1.25**；5G 细分支持度不足。因此这两类问题不会作为“渠道 + 产品”或“渠道 + 终端”重复输出。

## 数据分布与文本

| 项目 | 数值 |
| --- | ---: |
| 总用户 / 低分 / 高分 | 400 / 80 / 320 |
| 完整地址数 / 单一地址最多人数 | 160 / 3 |
| 终端厂商最大人数 | 134 / 400，33.5% |
| 终端型号最大人数 | 41 / 400，10.25% |
| 终端类型最大人数 | 200 / 400，50% |
| 有 `ts` / 空 `ts` 的触点 | 121 / 279 |
| 不同的客户原话 / 客服话术组合 | 311 / 107 |

终端厂商、型号和类型的单一取值占比，在全量、低分、高分集合以及每个分析分组内均不超过 50%。完整地址最多重复 3 次；若下游把地址归并到区县，归并后的频次会高于此值。

`voc_to_text_u` 使用客户口语表达办理经历、实际问题和诉求；`voc_to_text_s` 使用客服核查、解释与后续处理话术。`ts` 只在部分触点中有文本；空字符串表示该触点没有可用工单摘要，不用于断定是否建单。两类产品渠道问题的客户原话分别覆盖三个终端厂商；两类渠道单维问题覆盖四种产品和四个终端厂商，均不写成某个机型特有的故障。

每个用户 JSON 对象根节点均有 `channel_info` 数组，数组元素为 `{ "channel_code": "C101", "channel_name": "省营业厅小程序" }` 形式。当前每人只有一条订购 CSV 记录，所以数组恰有一个元素；其代码和名称逐人取自《业务订购.csv》同一行。原有三个分组继续使用 C101/C202，两类渠道单维问题使用独立的 C303/C404。

## 使用口径

- CSV 每行是一组真实配对的“用户、资费、渠道”。构造事务时应保留 DESIGN.md 的 `product_channel` 关系项，不要将多行订单展开为任意产品渠道组合。
- `mentioned_products` 来自用户原话；`资费名称` 来自订购 CSV。两者在本数据中一致，分析时仍应区分来源。
- CSV 保留原四列格式，没有办理时间、状态和生效时间。VOC 和 ts 中的订单状态是模拟触点叙述，不能代替可核验的订购流水。
- DESIGN.md 的组合白名单包含 `[channel]`、`[product, channel]` 和 `[product, channel, terminal_factory]`，且 `min_itemset_size = 1`，以便发现渠道单维模式；渠道单维分析读取根节点 `channel_info`。每个问题需先按 `action + main_object_l1 + main_object_l2` 分组，再计算支持度与 Lift。
